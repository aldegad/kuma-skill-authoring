もうAIエージェントを1つだけ使う時代ではありません。Codex、Claude Code、Grok、Hermes、Antigravity、Cursorは、どれも「スキル」とは何か、フックをどこに登録するか、どの指示ファイルを読むか、セッションをどう再開するかについて独自の考え方を持っています。同じツール群を手作業でそれぞれに配布すると、1週間もしないうちに食い違いが出てきます。

このリポジトリは、そのための方法論であり、事実にたどり着くための地図です。

1. **リポジトリが所有する唯一の信頼できる情報源を配布するための方法論**：スキル、フック、コマンド、スクリプト、ドキュメント、アセット、MCP/アプリの接続設定、プラグインメタデータを、食い違いなくすべてのランタイムにインストールします。そのために、1つの正規パッケージルート、シンボリックリンクによるインストール、単一の登録マニフェスト、明示的な廃止/リネーム手順、機械的に検査されるエンジン × ホームのパリティルール、検証チェックリストを用意しています。これが`SKILL.md`です。
2. **wikiの代わりの参照ガイド。** `docs/official-sources.json`は68件の公式ベンダーページをランタイム × 質問（`skills`、`hooks`、`plugins`、`project-instructions`、`cli-invocation`、`session-resume`、`model-lineup`、`billing`、…）で対応付け、`docs/lookup.md`はそれらを取得・判断・引用する方法を説明します。ベンダーの事実はここには一切保存しません。すべての回答は質問のたびにベンダーのページから読み取り、そのURLと日付を添えます。

## なぜwikiを持たないのか

このリポジトリは3か月間、出典付きの互換性wikiを維持し、毎日ベンダーのドキュメントから更新していました。その結果、2つのことがわかりました。1つ目に、エージェントが実際に読んでいたコピーは、更新処理が書き込んでいたコピーより9週間遅れていました。ミラーは、信頼されたまさにそのときに間違っているものです。2つ目に、本物のクロスランタイムの質問（「Claude Code、Codex、Grokで、中断されたターンは新しいプロンプトなしで続行できるか？」）が来た日、wikiには再開の*構文*は載っていましたが、答えは結局公式ページから得るしかありませんでした。ミラーは毎日の書き直しを必要とします。リンクなら取得1回で済み、間違うのはベンダー自身が間違っているときだけです。

残したのは、ベンダーが教えてくれないことです。すべてのランタイムにまたがって*あなた自身の*ツール群を1か所で管理する方法と、2つのエンジンが同じフィールドを異なる意味で読む数少ない箇所です。後者にはそれぞれ、再検証に使うソースIDを付けています。

## 何に答えられるか

| 質問 | 答えの出どころ |
|---|---|
| 「コピーを3つ作らずに、Codex、Claude、Grokのすべてがスキルを見つけられるようにするには、どこに置けばいい？」 | `SKILL.md` → Core Rules, Recommended Layout, Cross-Agent Install Pattern |
| 「フックを変更した。すべてのエンジン*と*すべてのアカウントホームに反映された？」 | `SKILL.md` → Engine × Home Is A Product：対象範囲を列挙するのはチェックリストではなく機械 |
| 「このスキルを1つのエンジンでだけオフにしたい / すべてで廃止したい / リネームしたい。」 | `docs/skill-lifecycle.md`、`SKILL.md` → Retiring Or Renaming Artifacts |
| 「PreToolUseガードが、Claudeではブロックしたのに、Codexではフェイルオープンしたのはなぜ？」 | `docs/hook-contract.md`：エンジン間の落とし穴を出典付きで |
| 「Hermesはどの指示ファイルを読む？ Antigravityはヘッドレスで動かせる？ Grokのセッションは何で再開する？」 | **参照（lookup）**：`docs/official-sources.json`から`agent` × `kind`でエントリを選び、ベンダーページを取得して引用する。`docs/lookup.md`を参照 |

**管理ツールはこのレイヤーの上に構築します。** Kuma Studioのスキル/フック切り替えシステムは、1つのGUIからClaude、Codex、Grok、Hermesのあらゆるスキルやフックをオン/オフできる仕組みで、この方法論の上に構築されました。各ランタイムの実際のオン/オフスイッチはベンダーページで確認しました。公式にスイッチが存在しない箇所では、推測で埋めずに、ツール側で意図的に補っています。

## 信頼できる理由

- **クロスランタイムに関するすべての主張は、ベンダー自身のドキュメントを引用します。** 引用は主張した時点で行い、日付を添えます。記載がない場合は`not documented (checked <urls>, <date>)`と記録し、他のランタイムから推測することはありません。
- **このリポジトリが所有するのは、自分たちのものだけです。** ルール、手順、そしてエンジン間の違いが私たちのスクリプトを壊しうる箇所です。そのいずれかがベンダーの挙動を前提にしている場合は、その行にマニフェストのソースIDを記載しているので、前提を取得1回で再確認できます。
- **地図へのリンクは機械が到達可能な状態に保ちます。** 週次ジョブが`scripts/check-official-sources.mjs`を実行し、移動したURLを修正してPRを開きます。決定論的なガードは、差分がドキュメントのみで、かつチェックに合格した場合にだけマージします（`docs/cloud-automation.md`）。

## このリポジトリが所有するもの

- `SKILL.md`：スキルのエントリポイント。作成/相互運用の方法論と、「ベンダーの事実は参照するもの」というルーティングルールを含みます。
- `docs/lookup.md`：ランタイムに関する質問に公式ページから答える方法と、マニフェストの保守方法。
- `docs/official-sources.json`：ランタイム × 質問ごとの公式URLのマニフェスト。各ページが答える質問も併記しています。
- `docs/authoring-rules.md`：各ルールの根拠と実際に計測されたインシデント、およびパッケージングの判断ゲート。
- `docs/hook-contract.md`：私たちのスクリプトが対処の前提としている、エンジン間のフックの落とし穴。
- `docs/skill-lifecycle.md`：無効化 / スコープ限定 / 廃止。
- `docs/skill-boundary-rules.md`、`docs/research-forge.md`、`docs/skill-repo-routing.md`、`docs/kuma-studio-patterns.md`：それぞれ、真実をどこで管理するか、ドキュメントベースのスキルをどう練り上げるか、自作またはフォークしたスキルの変更をどのリポジトリに入れるか、公開されているKuma Studioのパターン。
- `docs/cloud-automation.md`：週次のソースチェックと、その自動マージゲート。
- `CHANGELOG.md`とgitタグ：バージョンの記録。履歴はドキュメント本文ではなく、ここに残します。
